### Checked and clean, where the clean answer was not obvious

- **A Restore cannot misdirect a stale alarm.** `restoreFromBackup` calls `entryDao.deleteAll()`
  (`@Query("DELETE FROM entries")`) and re-inserts every entry with a *fresh* id — the snapshot
  mapper never carries `id`. Alarms armed before the restore are `PendingIntent`s keyed by the
  **old** ids, so if SQLite recycled ids, a stale alarm would fire against a different task and its
  Done/Skip action would resolve the wrong row. It does not: every id column is
  `INTEGER PRIMARY KEY AUTOINCREMENT` (checked in `25.json` for `entries`, `habits`, `reminders`,
  `blocks`) and a bare `DELETE FROM` leaves the `sqlite_sequence` row intact — run this session:
  three rows inserted (ids 1–3), `DELETE FROM t`, `sqlite_sequence` still `('t', 3)`, next insert
  id **4**. Both receivers also re-read the entry and return on missing or trashed. So 1.13's
  consequence is a *missed* notification, never a wrong one.
- **The merge does keep search in step.** The alarm seam is missed; the index seam is not —
  `PagesSyncEngine` calls `pageContentRepository.rebuildFtsForPage(pageId)` for every winning page
  in Pass 5 (`:669`), so a page that arrives from a peer is searchable immediately rather than at
  the next launch's `healIndex`. Worth stating because it is the same shape of seam as 1.3/1.13 and
  it is handled, which is what makes the alarm one an omission rather than a design.
- **The receivers' guards hold.** `OverdueAlarmReceiver` and `ReminderAlarmReceiver` both
  `getById(entryId) ?: return` and then `if (entry.deletedAt != null) return`, so an alarm
  outliving its entry costs a wakeup and nothing else.
- **The classic Kotlin shapes are absent.** Zero `GlobalScope`, zero empty `catch (e: X) {}`, zero
  `SimpleDateFormat` across `shared/src`, `Tendril android/app/src/main` and `Tendril windows/src`;
  four `runBlocking` sites, all at a start-up or window-open boundary, none on a hot path; the
  heaviest `!!` file has four. The `runCatching`-around-a-suspend-call hazard is reasoned about
  explicitly in `CalendarProviderSync.kt:175` and `SnapshotSyncOrchestrator.kt:1545`, and the
  remaining suspend-wrapping sites are all inside the sync pass, which runs `NonCancellable`.
- **The widget check-in goes through the shared use case**, not a reimplementation of the streak
  math, and refuses to write when App Lock is on. Only its re-arm is missing (1.12).
